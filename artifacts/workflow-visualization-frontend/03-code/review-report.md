## 必须修复

### CR-001：旧长任务结束后永久留在执行中

- 位置：`frontend/src/hooks/useConsole.ts:89`，相关接口 `host/state.ts:99`。
- 级别：`P1`，状态正确性。
- 触发：保持一轮较长时间执行，同时系统产生超过首页范围的新轮次。首页响应包括最新 `60` 轮和所有活动轮次，所以这个旧任务仍能出现在列表中；它结束后不再属于活动集合，也不在最新 `60` 轮中。
- 结果：`refresh` 总是用 `mergeRuns(old, result.runs)` 保留所有旧行，后端已经结束而未返回的旧行继续显示 `claimed`，不会被刷新为已完成。即使选中它读取 `why`，`run` 仍来自陈旧的列表行；会出现顶部运行数为零而列表和详情仍是执行中的矛盾，也不能正确呈现停止后的状态。
- 最小修复：区分已加载历史与先前活动记录。首页刷新发现先前活动轮次消失时，通过既有追溯数据等明确读取其最新状态，或以正确分页范围更新该行；不能仅将它推断为结束。保持单连接请求代次保护和用户历史列表。
- 必需回归：构造旧活动轮次在新首页消失的行为测试，证明其最终状态、摘要和可操作状态不再停留在旧值；先看到失败再修实现。

### CR-002：续接轮次过滤掉唤醒自己的卡片回答

- 位置：`frontend/src/model.ts:32`，后端依据 `host/runtime.ts:177` 与参考调用者 `cli/why.ts:71`。
- 级别：`P1`，流程追踪缺失。
- 触发：第 `1` 轮提出卡片，用户回答，回答事件唤醒第 `2` 轮。卡片的 `run_id` 始终是第 `1` 轮，而它的 `answer_event` 属于第 `2` 轮事件集合。
- 结果：后端 `why(2)` 有意返回 `answer_event` 属于本轮的前轮卡片；客户端却只收集 `run_id === 2` 的卡片编号，随后把前轮卡片的所有变更丢弃。新轮次详情看不到促成继续执行的问题、选项与实际回答，无法解释闭环。
- 最小修复：同时接受本轮创建的卡片和回答事件属于本轮的卡片，依据真实 `run_events` 关系保留必要事实；仍应排除同一事务中无关卡片与其他轮次。不应按规则名猜测关联。
- 必需回归：构造提问轮次与续接轮次不同的真实格式事实；断言续接详情保留准确的卡片与回答并排除无关卡片。前一轮详情也应继续可见原问题与回答。
