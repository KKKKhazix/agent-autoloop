# 等导出就绪时，何时需要唤醒 Agent？

已有长会话用 `later` 等外部恢复的实例，每次复查都要重新读取上下文。先用 `agent-autoloop wakeups [规则] [--limit 100] [--json]` 查看自己的历史。找出反复复查的规则后，用输出中的轮次编号运行 `agent-autoloop why <编号>`，核对这些轮次是否只在观察同一个外部状态。[社区案例 #268](https://github.com/KKKKhazix/agent-autoloop/issues/268)

## 读报告

- 默认检查最近 100 条轮次历史。可以按规则筛选，或增大 `--limit`。报告排除尚未结束和从未被领取且没有用量的轮次。
- 每条规则按到期复查、人工回答、混合、其他或来源未明分组。真正的复查和回答通过事件与定时器、卡片的关联核对。多种原因合并成的一轮只计一次。
- 每组列出有过失败的轮数和最多三个最近的轮次编号。一次轮次可以有多次尝试，命令型 Agent 也会产生轮次；具体执行器可以在 `why` 的时间线核对。
- 用量来自已保存的轮次。每项分别报告已知值合计及覆盖的轮数。输入已含缓存读取，二者口径可比较时才相减；费用未上报显示为缺失。旧适配器的统计口径可能不同，跨版本比较时请记录版本。
- 多次复查只是核对线索。是否有必要调用模型取决于业务状态和产物，例如人工回答后续办通常需要保留上下文。

## 复现对照实验

在仓库根目录使用 Node 24+。默认模式以确定性函数代替模型。添加 `--codex` 会调用本机已登录 Codex，使用模型额度。两组共预期四次真实启动，每次限时两分钟。

```sh
node examples/recipes/export-wait/compare.ts
node examples/recipes/export-wait/compare.ts --codex
```

实验为两组分别建立临时工作目录和内存中的 Autoloop 内核。两组都有四次观察机会，使用相同的虚拟时钟和导出数据。前两次文件尚未生成，第三次文件出现，第四次仍能观察到同一个文件。

| 策略 | 文件未就绪 | 文件就绪、再次就绪 |
| --- | --- | --- |
| `later` | Agent 每次返回 WAIT，实验驱动将它转换为下一分钟的 `later` 回执 | Agent 在原会话核算导出，并结束复查 |
| `probe` | 脚本检查文件是否存在 | 每次观察都提交相同的来源事件 ID，中台去重后只唤醒一次 Agent |

两组都必须恰好产出一份摘要，包含 3 行、总和 41。提前交付、漏处理、重复产物或数值错误会使实验失败。自动测试另覆盖文件始终未生成时的行为。生产环境应由生产者在完整写入后原子发布文件，或提供明确的就绪标记，并为每个独立导出使用稳定且唯一的事件 ID。

输出的 `calls` 是各组调用执行器的次数，`products` 是验收过的摘要，`readyLagTicks` 是相对就绪时点的探测间隔数，`readyLagMs` 是本次自文件出现至拿到结果的实测毫秒数。真实模式沿用本机模型配置和相同的推理强度；`usage` 按调用报告增量，缺失值保留为空。两组固定先后执行，缓存命中及服务延迟可能不同。真实模式在内存调度器旁直接运行 Codex 适配器，只使用合成的导出快照；HTTP、通知送达和真实导出服务各有独立验证范围。
