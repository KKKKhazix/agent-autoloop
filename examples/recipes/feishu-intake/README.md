# 从飞书私聊提交需求

机器人私聊里发「多站点：核对站点详情」，接入程序用飞书的消息编号把需求登记到中台，再回一条带轮次号的消息。完成卡片由现有飞书通道发送。

飞书自建应用启用机器人、私聊收消息权限和长连接事件 `im.message.receive_v1`。使用交互卡片时还要订阅 `card.action.trigger`。在中台登记专用来源，规则只匹配 `operations.requirement`。首轮可以用只读 Codex 做需求梳理。规则写 `parallel: 1`，让不同消息排成独立轮次，且同一时间只执行一轮。设 `tell: "always"` 并给规则指定飞书通道。若已有其他规则，检查默认通道路由，避免把原有任务通知发到新通道。

将 `url`（本机中台的 HTTP origin）、`key`（专用来源密钥）、`owner`（允许提交的用户在当前应用下的 open_id）、`lark`（lark-cli 的绝对路径）放入本机权限为 0600 的 JSON。凭据和真实资料留在本机。以已登录的机器人环境运行：

```sh
node examples/recipes/feishu-intake/intake.ts /absolute/path/to/private-config.json
```

用系统服务监管进程并保存状态日志，服务停止时正常发送 SIGTERM。每个应用只在一台接入机上消费。启动后用本人私聊提交一条测试需求，核对回执中的轮次号、`agent-autoloop why <轮次>` 和最后的飞书卡片。若提交失败或未收到确认，可再次发送需求并在中台核对已有轮次。相同飞书消息的重复投递由中台按来源和消息编号去重。

## 确认后开发

用「多站点开发：」提交开发需求。为同一来源的 `operations.development` 事件单独配置规则，设置 `parallel: 1` 和飞书通道，将执行器设为 `use: "command"`。命令参数为 Node、`development.ts` 的绝对路径和本机私有配置路径。配置填写 `owner`、`workspaceRoot` 和 `runner`。工作区父目录须由本人提前创建并保护。

开发规则先发「确认开工」卡片。只有对应卡片的授权用户选择「确认开工」才启动本机配置的执行程序，选择「取消」则结束。执行程序收到独立工作目录和需求资料文件两个参数，负责复制可信项目基线、执行改动并运行定向验证。程序只在改动和验证都通过时返回 0。验证失败时，项目执行器可在同一工作区定位原因、修复并重跑相关检查。工作区保留日志，执行结束后中台把结果发回飞书。重复派发沿用已保存的回执。开发成果交付到本机隔离工作区。

执行程序最终未通过，或上次留下工作区却没有完整回执时，发「开发未完成，怎么继续」卡片等待决定，不自动重跑。选择「保留原工作区，重新执行」会从项目基线新建一次工作区，原代码和日志保留供核对；选择「结束」则停止续办，可人工接手。一次重新执行绑定这张确认卡片，重复投递只重放该次回执，不重复运行程序。成功才发仅告知通知，失败继续留问题卡片。

旧版保存的「开发或验证未通过」仅告知回执，在再次执行对应任务时转成上述续办问题；不改原工作区，也不自动重新开发。
