# 全量修复与性能优化实施计划

## Context（背景与目标）

基于对仓库（HEAD `871e778`）的完整代码审计与本机实测（Apple M6 / Node v24.22.1），当前项目存在 4 类实测性能退化、5 项工程边界隐患及 3 处文档/基准脚本不一致：

1. **深队列写放大**：排队 5000 条时，每次产生事实（`ingest` 24.6 ms、`claim` 33.0 ms、`finish` 24.4 ms）都会在 `deadlines()` 中全表拉取并反复 `JSON.parse` + 递归 `Object.freeze` 整张 `queued` 表（`1 + W` 遍）；组占满时空领活（`blockedClaim` 10.4 ms）也每次扫全表。
2. **历史增长退化未彻底消除**：`/v1/state`（查各通道最新投递）和 `/v1/metrics`（统计失败/放弃投递）在 `deliveries` 上缺少匹配索引，每次仍全表扫描历史投递记录；`events` 按来源计数仍扫全量索引叶子。历史涨 5 倍时 `/v1/state` 延迟从 4.46 ms 涨至 13.63 ms。
3. **长轮询惊群、未缓存 SQL 与重复鉴权**：`host/server.ts` 的 `wake()` 不区分领活与通道等待者，唤醒回睡时逐个同步触发 `arm()`；`host/runtime.ts` 的 `all()`/`one()`/`logAfter()` 未复用 `StatementSync` 预编译缓存；`callerOf()` + `requireKey()` 单次请求最多全表查 5 次 `keys`。
4. **Worker、GitLab 交付与纯洁性测试缺口**：Worker 交回执遇 HTTP `5xx` 无退避（每秒紧循环重打）、`groupAlive()` 用同步 `execFileSync("ps -ax")` 阻塞事件循环、`worker/usage/` 永不清理、每轮 `tick` 重复读 3 遍 `entry.json`；GitLab 交付缺 `git fetch` SHA 缓存、`prepareShip` 和 API 分页；6 审查器串行上限（6×30=180m）撞上 Worker 180m `SIGKILL` 线且强杀残留临时目录；`tests/purity.test.ts` 前三项扫描未加 `{ recursive: true }`。
5. **基准与文档滞后**：`scripts/history.ts` 重建哈希漏验 `projection_tallies`；`scripts/benchmark.ts` 未测带容量（`capacity=1`）长轮询并发唤醒；`docs/protocol.md` 残留旧的硬门槛表，`README.md` / `README.en.md` 内核行数与复现说明滞后。

**目标**：在不破坏任何 `/v1` 协议、插件约定与现有行为规格的前提下，把深队列热路径压回 ~1 ms 量级，让 `status` 与 `/v1/metrics` 真正实现历史 `O(1)`，补齐全部工程隐患与文档口径，并通过全套 `test` + `test:nightly`（模拟、穷举、强杀、变异）与独立 Agent 盲审。

## 约束与原则（严格对齐仓库 AGENTS.md）

- **测试先行**：每个阶段先在对应 `tests/*.test.ts` 写清防的失败方式与失败测试，再写实现；一个行为一条测试，不改已有行为规格预期。
- **不写数据迁移**：投影表或索引变化只改 `kernel/evolve.ts`（`host/fingerprint.ts` 自动识别指纹变化并按 5 万条分块从事实日志重建）。
- **克制边界**：遵循“代码只写现在需要的，不无依据加兜底”——清理闲置 `worker/usage/*.json`，但**不强行截断或强杀运行中正常输出大量 `stream-json` 的 Agent 日志**，避免误伤长程编码会话。
- **变异与纯洁性零妥协**：改动 `kernel/` 后同步核对 `sim/mutate.ts` 全部变异点（确保原版全过、每个变异均非语法错误且 100% 被检出），严守 `kernel/` 零外连、零时钟、零文件系统、零产品名。

## 分阶段实施方案

### 阶段 0：计划落盘与任务台账
- 审批通过后，将本计划写入 `docs/plans/2026-11-18-perf-and-audit-fixes.md`，并通过 `TodoWrite` 逐阶段跟踪对账。

### 阶段 1：消除 `/v1/state` 与 `/v1/metrics` 的历史扫描（真 `O(1)`）
- **先补测试**：
  - `tests/metrics.test.ts` / `tests/http.test.ts`：验证大量已完成历史投递与来源事件下，通道最后一次失败状态、`/v1/metrics` 失败/放弃计数、各来源事件总数与重建前后完全一致。
- **修改文件**：
  - `kernel/evolve.ts`：
    1. 将 `indexes.deliveries` 从 `[["channel"], ["card_id"]]` 升级为 `[["channel", "card_id"], ["card_id"]]`（使按通道逆序取最大 `card_id` 走单次 B-Tree 定位）。
    2. 新增部分索引 `projection_delivery_trouble`（仅覆盖 `given_up=1 OR error IS NOT NULL` 的异常投递行，正常送达行零索引开销）。
    3. 新增派生计数表 `projection_sources(source TEXT PRIMARY KEY, count INTEGER NOT NULL)`，在 `evolve()` 写入新 `events` 行时同步累加，`reset` 时清空（同 `projection_tallies` 模式）。
  - `host/state.ts`：
    1. `lastDeliveries` 改为按已配置通道执行 `SELECT channel, card_id, tries, error, given_up FROM deliveries WHERE channel = ? ORDER BY card_id DESC LIMIT 1`，消除全表双扫与临时 Bloom Filter。
    2. `sources` 事件计数改为单次读取 `SELECT source, count FROM projection_sources`。
  - `host/metrics.ts`：
    1. `deliveries` 汇总查询加上 `WHERE given_up = 1 OR error IS NOT NULL`，精确命中 `projection_delivery_trouble` 部分索引。
  - `scripts/history.ts`：
    1. `rebuild` 一致性哈希列表补齐 `"projection_tallies"` 与 `"projection_sources"`。

### 阶段 2：消除深队列 `O(W × Q)` 写放大与 `blockedClaim` 全表扫
- **先补测试**：
  - `tests/queue-costs.test.ts`：新增行为断言——排队深度从 1 涨到 200 时，`ingest`、`claimNext`（含组并发占满被挡回）、`finish` 与 `deadlines` 解析的 `runs` JSON 行数保持常数级（不随排队长度线性增长），包括时钟回拨与离线卡片关闭后的新任务场景。
- **修改文件**：
  - `kernel/evolve.ts`：
    1. 扩展 `Match` 支持 `{ gt?: SQLInputValue; lte?: SQLInputValue }` 范围条件（同步支持内存 overlay `accepts()` 与 SQL `json_extract` 比较）。
    2. 为 `runs` 增加复合索引 `["state", "not_before", "id"]`、`["agent", "state", "id"]`、`["rule", "state", "id"]`（均使用标量等值前缀以保持 `$.id` 索引有序 `LIMIT` 早停，不触发临时 B-Tree 排序）。
  - `kernel/due.ts`：
    1. `retry` 到期仅查询 `{ state: "queued", not_before: { gt: iso(now) } }`，正常排队行零解析。
    2. 循环外单次读取 `claimed = rows(view, "runs", { state: "claimed" })`。
    3. 对每个 `worker`，只按其名下 `agent` 各取 `LIMIT 1` 最早就绪排队轮次（`{ agent, state: "queued", not_before: { lte: iso(now) } }`）以判定是否有活及最早 `created_at`；仅当存在已关闭的离线卡片（`card && card.state !== "open"`）时，额外以 `created_at: { gt: card.closed_at }` 取 `LIMIT 1` 传入 `offlineCard()`，完整保留 `offlineCard` 原表达式与时钟回拨正确性。
  - `kernel/decide.ts`：
    1. `claimNext()` 先只读 `claimed` 行并检查 `held` 重领；再遍历规则配置筛出当前 `worker` 可领、未禁用、未暂停且组/规则/Agent 并发未满的候选规则。若无候选规则（如 `blockedClaim`），直接返回 `null`（零 `queued` 查询）。
    2. 对每个候选规则，按 `{ rule: rule.name, state: "queued", not_before: { lte: draft.at } }` 仅取 `LIMIT (该组已占槽位 + 1)` 条候选，选出跨规则最小 `id` 且 lane 未被占用的那一轮。
  - `sim/mutate.ts`：
    1. 核对并同步 `group-capacity`、`lane-exclusion`、`retry-deadline`、`offline-*` 的匹配片段，确保全部变异 100% 有效且被检出。

### 阶段 3：长轮询分流唤醒、`arm()` 防抖、外壳 SQL 缓存与单次鉴权
- **先补测试**：
  - `tests/http.test.ts`：验证纯通道投递动作（`delivered` / `channelSeen`）不会唤醒挂着等活的 `/v1/work` 长轮询，纯轮次心跳/启动（`started`）不会唤醒 `/v1/cards/next`；验证开启 `limits` 时轮次令牌与各类访问密钥行为不变。
- **修改文件**：
  - `host/runtime.ts`：`all()`、`one()`、`logAfter()` 全部改用 `statement(db, sql)` 复用预编译语句，消除 `/v1/state` 循环与 `/v1/stream` 逐条重编 SQL。
  - `kernel/http.ts` & `host/server.ts`：
    1. `Services.wait(until, signal, kind?: "work" | "card")` 增加可选类型参数（兼容现有测试桩），`host/server.ts` 拆分等待集合，按变更涉及的表精准唤醒对应集合。
    2. `wait()` 触发的 `arm()` 通过 `queueMicrotask` 合并防抖（同一事件循环批次百千连接回睡只算一次 `MIN(at)`），并用普通循环替代 `Math.min(...array)` 消除大数组展开栈风险。
  - `kernel/evolve.ts`、`kernel/credentials.ts` & `host/server.ts`：
    1. `View` 实例级缓存基础 `keys` 行列表（同 `View.configs` 模式，每次新事实产生新 `View`，绝不陈旧）。
    2. `callerOf()` 对无匹配密钥的 `/v1/runs/:id/(started|result)` 快速归类，单请求内只读一次 `keys`。

### 阶段 4：Worker 退避、异步进程组探针、单轮读取合并与 `usage/` 清理
- **先补测试**：
  - `tests/worker.test.ts`：
    1. 新增测试：中台对 `result` 返回 HTTP `500`（`HubError(500, ...)`）时，Worker 保留结果并退避 30 秒再重交，不在每秒心跳轮询中紧循环重打（同时保持普通断网 `Error` 原有行为不变）。
    2. 新增测试：`tidy()` 清理超过 14 天未更新的 `worker/usage/*.json`，但近期使用或刚读取过的会话用量文件保留。
- **修改文件**：
  - `worker/worker.ts`：
    1. `settle()` 中捕获 `error instanceof HubError && error.status >= 500` 时写入 `entry.retryAt = now() + BUSY_PAUSE` 并持久化。
    2. `groupAlive()` 中将同步 `execFileSync("ps", ["-ax", ...])` 改为异步 `execFileAsync`（`promisify(execFile)`），避免阻塞与中台共用的事件循环。
    3. `tick()` 合并 `entries()` 读取，减少每轮重复的目录扫描与 `JSON.parse`。
    4. `tidy(moment)` 中调用 `tidyUsage(moment)`。
  - `worker/usage.ts`：
    1. `loadUsage()` 读取成功时顺手 `utimesSync` 刷新文件修改时间（防止跨数周仍在续接的长寿会话基线被误删），新增 `tidyUsage(moment, keepMs)` 清理超期文件。
